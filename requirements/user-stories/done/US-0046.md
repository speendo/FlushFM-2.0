# US-0046: Light-Driven State Transitions (Event-Driven)

> **Status:** Done | **Priority:** High | **Created:** 2026-06-07 | **Depends on:** US-0045

## User Story
As a **user**, I want **the device to automatically start playing when the room becomes bright and return to standby when it becomes dark**, so that **the radio powers on when I enter the room and off when I leave without any manual interaction**.

## Acceptance Criteria

### Light State Change Propagation
- [x] `LightSensorComponent` monitors light state changes in its `poll()` method via the `LightSensor::readState()` call
- [x] When `readState()` returns `BRIGHT` and the last seen state was `DARK` (or uninitialised), the component posts a `postStateRequest(SystemState::LIVE)` to the Supervisor
- [x] When `readState()` returns `DARK` and the last seen state was `BRIGHT` (or uninitialised), the component posts a `postStateRequest(SystemState::READY)` to the Supervisor
- [x] State requests are only posted on state **change** (not re-posted on every poll cycle while the same state persists)
- [x] Light-driven transitions respect the Supervisor's current state contract — no request is posted if already in the target state
- [x] `LightSensor::readState()` uses internal hysteresis (latched value, see US-0045) — the component itself never sees a third state, so no `HYSTERESIS_GAP` handling is needed in the component

### Event-Driven Architecture (No Polling Loop Outside `poll()`)
- [x] Light state changes are detected only within the component's existing `poll()` hook (called by the Supervisor's loop)
- [x] No additional FreeRTOS task is created for light sensing
- [x] No `delay()` or blocking loops are introduced — `poll()` returns quickly on every tick
- [x] The `LightSensor` library's `readState()` call itself is non-blocking and lightweight (a single `analogRead()` plus comparison)

### Deep Sleep Wake Path (Future Readiness)
- [x] As a future-proofing measure, `handleSLEEP()` calls `LightSensor::configureUlpWake()` to prepare the sensor for ULP monitoring (implementation may be a stub/TODO if ULP scaffolding does not yet exist)
- [x] A `#define LIGHT_SENSOR_WAKE_ENABLED 0` compile-time flag gates the ULP wake code path — set to 0 until hardware-validated
- [x] The ULP wake stub is documented in the component header with pin, threshold, and wake-trigger notes so the next implementer has a clear integration point
- [x] No functional ULP code is required in this story unless ULP scaffolding already exists in the codebase — the goal is to leave a clean integration surface

### Native Tests
- [x] `LightSensorComponent` native tests (using a mock `LightSensor` interface) cover:
  - BRIGHT→DARK transition posts `postStateRequest(READY)` exactly once
  - DARK→BRIGHT transition posts `postStateRequest(LIVE)` exactly once
  - Same state re-read on consecutive poll cycles does not post any state request
  - No request posted when system is already in the target state

### Validation
- [x] `pio test -e native` passes with new component tests and all existing tests
- [x] Debug build compiles successfully
- [x] Production build compiles successfully
- [x] On hardware (optional): cover/uncover sensor, observe state transitions via serial log; verify no oscillation at threshold boundary

## Notes
- The Supervisor's Mailbox is last-write-wins — if a light-driven request races with a manual CLI command, the most recent write prevails, which is the correct behavior for user-override scenarios
- The `LightSensor` library itself does NOT post events — it only provides raw/state readings. The `LightSensorComponent` wrapper is responsible for translating sensor readings into Supervisor state requests, maintaining the separation of concerns from US-0045
- For deep sleep wake: the ESP32-S3 ULP RISC-V coprocessor can monitor ADC1 and trigger wake. The stub left by this story provides the hook; a follow-up story will implement the actual ULP program
- `readState()` is called once per Supervisor loop tick (~every few ms) — this is not "constant polling" in the problematic sense; it is the standard component poll pattern already used by WiFi and Audio components
- If the user manually changes state via CLI (e.g., stops playback), the light sensor should NOT immediately override it — the sensor tracks its own last-stable-state to avoid fighting user intent. On the next genuine light change (bright→dark or dark→bright), it will re-assert the appropriate state
- Target state guard: the component tracks the last state request it posted; if the system is already in that state (observable via Supervisor), it suppresses redundant requests
