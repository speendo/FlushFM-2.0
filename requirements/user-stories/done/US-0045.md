# US-0045: TEMT6000 Light Sensor Component and CLI Diagnostics

> **Status:** Done | **Priority:** High | **Created:** 2026-06-07

## User Story
As a **developer**, I want **the TEMT6000 light sensor wrapped as a standalone `LightSensor` component under `lib/` with debug CLI commands to read raw values and thresholds on demand**, so that **sensor hardware and ADC wiring can be validated independently before integrating it into the system state machine**.

## Acceptance Criteria

### Component Library (`lib/LightSensor/`)
- [x] Pure virtual interface `ILightSensor` with methods `readRaw()`, `readZone()`, `readState()`, `setThresholds()` — all core logic is host-testable via mock implementation
- [x] Concrete `LightSensor` class implements `ILightSensor`, wrapping `analogRead()` on ADC1
- [x] `begin()` initialises ADC1 on `LIGHT_SENSOR_PIN` (defined in `src/core/config.h`) with 12-bit resolution and 11 dB attenuation
- [x] `readRaw()` returns the instantaneous raw ADC value (no latching or threshold logic)
- [x] Threshold configuration: `setThresholds(brightToDark, darkToBright)` — validity enforced at set-time: `darkToBrightThreshold >= brightToDarkThreshold`; returns false if rejected
- [x] `readZone()` returns the instantaneous light zone based on the raw reading vs thresholds: `BRIGHT` (raw > `darkToBrightThreshold`), `DARK` (raw < `brightToDarkThreshold`), or `HYSTERESIS_GAP` (raw between the two thresholds)
- [x] `readState()` returns the latched stable `LightState` — always `BRIGHT` or `DARK`, never a third value. An internal latched variable changes only on threshold crossing:
  - Latches to `BRIGHT` when `readZone()` returns `BRIGHT`
  - Latches to `DARK` when `readZone()` returns `DARK`
  - Holds the last latched value while `readZone()` returns `HYSTERESIS_GAP`
- [x] Default thresholds are compile-time constants; runtime `setThresholds()` changes are lost on reboot (NVS persistence deferred to US-0038)

### Component Registration (Supervisor Wiring)
- [x] `ComponentID::LightSensor` added to the `COMPONENT_ID_X` X-macro in `src/component_types.h`
- [x] New `LightSensorComponent` class in `src/components/composition/system_components.h/.cpp` inheriting from `ISystemComponent`
- [x] Constructor takes `ILightSensor&` via dependency injection (same pattern as `AudioRuntimeComponent` with `IAudioPlayer`)
- [x] Component marked as `required` — sensor absence triggers ERROR recovery
- [x] All `handleX()` state handlers implemented: sync completion for `BOOTING`, `CONNECTING`, `READY`, `LIVE`, `ERROR`, `FATAL`; `handleSLEEP()` completes and disables the sensor if relevant
- [x] `setup()` calls `sensor_.begin()`, registers with Supervisor, returns `true` — no runtime hardware detection (TEMT6000 is a passive phototransistor with no distinguishable failure mode)
- [x] Component instantiated and wired in `src/main.cpp` alongside other components

### CLI Diagnostics (Debug-Only Commands)
- [x] Debug CLI command `light thresh <brightToDark> <darkToBright>` added in `src/components/cli/debug_cli.cpp` — updates both thresholds at runtime; rejects if `brightToDark > darkToBright`
- [x] Debug CLI command `light status` added in `src/components/cli/debug_cli.cpp`
- [x] On invocation, enters a continuous output mode: prints one status line per cycle showing raw ADC value, zone (BRIGHT / DARK / HYSTERESIS_GAP), latched state (BRIGHT / DARK), and both threshold values
- [x] Repeated output continues until the user sends `x` or `exit` on the serial line, which cancels the mode and returns to the normal CLI prompt
- [x] All light commands are debug-only (within `#ifdef DEBUG_ENABLED`)

### Native Tests
- [x] `lib/LightSensor/test/` contains native tests covering:
  - `readRaw()` returns correct value given a mock ADC reading
  - `readZone()` returns BRIGHT when raw > `darkToBrightThreshold`
  - `readZone()` returns DARK when raw < `brightToDarkThreshold`
  - `readZone()` returns HYSTERESIS_GAP when raw is between the two thresholds
  - `readState()` latches to BRIGHT on crossing above `darkToBrightThreshold` and holds through gap
  - `readState()` latches to DARK on crossing below `brightToDarkThreshold` and holds through gap
  - Threshold setter rejects `brightToDarkThreshold > darkToBrightThreshold`
  - Threshold setter accepts `darkToBrightThreshold >= brightToDarkThreshold`
- [x] Tests compile and pass in the `native` PlatformIO environment (`pio test -e native`)

### Validation
- [x] `pio test -e native` passes with new sensor tests and all existing tests
- [x] Debug build compiles successfully
- [x] Production build compiles successfully (debug CLI commands stripped)

## Notes
- The sensor uses ADC1 only (ADC2 is unavailable when WiFi is active per `hardware.md`)
- The light sensor is **required** hardware — if absent or undetected at boot, the system enters ERROR recovery
- No runtime hardware detection: the TEMT6000 is a passive phototransistor; a zero reading is valid in darkness and a max reading is valid in bright light. Detection is a build-time concern — if the pin is in `config.h`, assume the sensor is present
- The `LightSensor` library should remain independent — it does not know about the Supervisor or SystemState. State-change events are the responsibility of the `LightSensorComponent` wrapper
- Default thresholds TBD empirically — start with conservative values and document calibration procedure
- Thresholds are runtime-only in this story; NVS persistence is covered by US-0038
- This story deliberately keeps sensor integration with the state machine out of scope (see US-0046)
- The hysteresis pattern (two thresholds with a dead band) prevents oscillation when light levels hover near a single threshold value
